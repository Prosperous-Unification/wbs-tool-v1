## Context

The scheduler (`libs/domain/src/schedule.ts` — it moved out of be-01 on 2026-09-02) is a deterministic millisecond pass (Fast). It is immediately visible, the sole fallback, and never labelled optimal. WBS has no optimization today. Dany approved adding an optional dual-objective mode using official OR-Tools CP-SAT. Architecture section 1 (toggle, PRI+Time concurrency, exact-hash SQLite cache, one generation per project) and sections 2-4 (behaviour, failure, test design) are all approved; this design records the settled technical shape.

## Goals / Non-Goals

**Goals:**

- Compute Priority-first (PRI) and Finish-first (Time) schedules with a real constraint solver, concurrent, behind a project-wide OFF-by-default toggle.
- Keep Fast unchanged as the preview and fallback.
- Cache validated results in durable SQLite; broadcast newly stored results so collaborators converge.
- Surface a compact comparison indicator without a toast or modal.

**Non-Goals:**

- No proven optimality (best-found only).
- No daemon, port, sidecar, or outbox.
- No fix to the known capacity/floor hand-off audit finding.
- No timer retry; no per-user objective.

## Decisions

- **Runner:** official OR-Tools CP-SAT in its own versioned Python package `wbs-solver`, invoked by Bun as a short-lived stdin/stdout CLI. No import, no daemon, no HTTP port.
- **Concurrency:** optimization ON computes PRI and Time concurrently for one canonical input. Engine Fast/Optimized and Objective Priority-first/Finish-first only select which cached output is displayed.
- **Objective mathematics and the priority numeric domain (Sol r6 Important 9; Sol r11 Critical 2):** `MAKESPAN = max finish`; `MOVEMENT = Σ |start(s) − baselineStart(s)|` against the quantised baseline; `PRIORITY = Σ w(s)·finish(s)`. The previous weight `w(s) = (P_max + 1) − p(s)` was unsafe on legal data: `asOptionalPriority` accepts any safe integer ≥ 1 with **no product ceiling**, so `P_max + 1` already loses integer precision at `Number.MAX_SAFE_INTEGER`, and multiplying that weight by a finish and summing over slices overflows CP-SAT's signed 64-bit linear expressions. Priority is an **ordering** in this product, not a metric, so the weight is now the **dense rank of the priorities actually present in the canonical input**: let `D` be the sorted set of distinct resolved leaf priorities and `R = |D|`; then `w(s) = (R + 1) − rank(p(s))` with `rank` 1-based ascending, and `w(s) = 0` for a leaf with no priority above it. This preserves every pairwise ordering the raw numbers expressed and bounds the term by `Σ w(s) × horizonUnits ≤ N·(N+1)·horizonUnits`. **Bun/JSON exactness is the tighter bound:** the request builder computes exact worst cases for `PRIORITY` and `MOVEMENT` and refuses before spawn with `objective-overflow` if either exceeds `Number.MAX_SAFE_INTEGER`. Every **wire** request/response `value`, `stageValue`, `bound`, `PRIORITY`, `MAKESPAN`, and `MOVEMENT` must be a non-negative safe integer in quantised solver units; an unsafe response is `invalid-output`. That is the _wire_ rule only; the numeric domain of a **stored** term is decided by its row's `publication` and is stated in the cached-row decision below (Sol r12 Critical 1). This retains ample CP-SAT headroom and, unlike the former `2^62` ceiling, lets Bun recompute and compare a one-unit difference exactly. `R = 0` — no leaf carries a priority anywhere — makes every weight zero, so `PRIORITY` is identically zero, stage 1 is vacuous, and PRI degenerates to Time. **The resolver is Fast's, and it is a nearest/most-specific override rather than a floor (Sol r8 Critical 7).** `priorityByLeaf` walks from the leaf upward and takes the **first non-null** value, so the most specific statement wins in _both_ numeric directions: leaf 5 under parent 1 resolves to 5, and a floor/minimum reading would produce 1 and optimize a different objective. The request builder in `libs/contracts/solver` **must not reimplement this**; `priorityByLeaf` **must be exported** from `libs/domain` — it is declared unexported today and `libs/domain/src/index.ts` re-exports only what `schedule.ts` exports, so tasks slice 2.0 publishes it before 2.2 imports it (deepseek r9 Important 1) — and both call sites then use the one function. The named request-weight cases cover a leaf overriding its parent in both numeric directions, a nearer ancestor overriding a farther one, and an unprioritised leaf. The numeric boundary fixture accepts an exact `Number.MAX_SAFE_INTEGER` sum, refuses one greater before spawn, and rejects a response changed by one rather than rounding both values together. PRI minimizes `(PRIORITY, MAKESPAN, MOVEMENT)` lexicographically, Time minimizes `(MAKESPAN, PRIORITY, MOVEMENT)`. These are **not** total orders: ties exist and production is not required to break them reproducibly.
  The preflight bound accumulator uses `bigint` internally and compares against
  `BigInt(Number.MAX_SAFE_INTEGER)` before converting to wire numbers; it never
  multiplies or sums into an already-inexact JavaScript `number`.

Every stage installs the previous stage's incumbent as a solution hint.   **`value` is the term's value on the published schedule; `stageValue` is what that stage proved (Sol r7 Critical 1).** The earlier matrix reported the stage incumbent `v` as `value`, while task 2.4 and the wire contract require Bun to recompute every objective value from the final offsets and reject a mismatch as `invalid-output`. Those cannot both hold, and the case is not hypothetical: stage 2 minimises `T₂` under `T₁ ≤ v₁`, and a solution with a strictly _better_ `T₁` is inside that feasible region, so a legitimate later-stage improvement makes the final schedule's `T₁` smaller than `v₁`. Under the old schema the solver had to choose between encoding a false `value` and having its own valid answer rejected. The four fields are therefore distinct and all four are in `solver-wire.v1.json`: `value` — the term recomputed on the published offsets, and the **only** field Bun re-validates by recomputation; `stageValue` — the incumbent that stage found, `null` when it found none; `bound` — that stage's best dual bound; `status` — `'optimal' | 'feasible' | 'unknown'`, a statement about the _stage_, never about the published schedule. Bun additionally checks the one relation that must hold, `value ≤ stageValue` when both are present, since every later stage's constraint is an inequality at `stageValue`; a `value` **worse** than the stage's own incumbent is a real contract violation and stays `invalid-output`. `'optimal'` therefore keeps its exact meaning — the stage proved `stageValue` optimal for its own restricted problem — and never claims the published schedule is optimal, which the design has said from the start it is not.

  **The response-level `status` is generated from this matrix's _rows_, not from its first _column_ (settled 2026-09-03; it was the last member of `solver-wire.v1.json` with a meaning and no shape).** The per-term `status` above answers "how strong is this stage's proof"; the response `status` answers a different question — "is a schedule being returned at all, and if not, which of the two reasons applies" — so it is a **run-outcome** vocabulary of exactly three values, `feasible | unknown | infeasible`, and each was read off an artifact rather than chosen. `infeasible` is pinned verbatim by the spec's "SHALL admit `infeasible` as a first-class outcome"; `unknown` is pinned by the same sentence's "SHALL NOT be mapped onto `unknown`", which only means something if `unknown` is itself a response status; `feasible` is the only other outcome any row produces, since every publishing row publishes an incumbent and an incumbent is feasible by construction. **`optimal` is excluded, and by this design's own words rather than by taste:** the paragraph above says the per-stage `'optimal'` "never claims the published schedule is optimal, which the design has said from the start it is not", and a response-level `optimal` would make exactly that claim. That closes the candidate of reusing the stage vocabulary plus `infeasible`. Proof strength is already carried per term and is not reported twice.

  **The `status`-to-payload conditional falls out of the `n/a` column.** `feasible` carries `offsets` **and** `objectiveValues`; `unknown` and `infeasible` carry **neither**, because all three stopping rows write `n/a` and `value` is by definition the term recomputed on the _published_ offsets — with nothing published, all three `value` fields have no referent. `offsets` is **absent** rather than `{}`: an empty map is a well-formed offset map, so it would pass the schema and fail the key-set invariant one layer later, reporting a vocabulary decision as a corrupt payload.

  **A later-stage INFEASIBLE therefore has no encoding on the wire, deliberately.** The `INFEASIBLE, k > 1` row's own argument is that every constraint a later stage adds is already satisfied by the previous incumbent, so the result "cannot become infeasible unless the model is wrong" — meaning the solver, at that moment, holds a counterexample to its own solver's answer. `infeasible` on this wire means one thing only, a proof about the submitted constraint system, so the solver **SHALL exit non-zero without emitting a response** rather than emit a proof it can itself refute; the coordinator records that run as `invalid-output`, which is the disposition this row already assigns. **Falsifier:** any artifact that requires the coordinator to distinguish "the solver crashed" from "the solver contradicted itself" _from the response_ — that would need a fourth status, and this decision chose wrong.

  The `k > 1` UNKNOWN-without-incumbent row is the case the earlier prose decided two ways: a valid anytime result is **kept**, not discarded as `no-solution`. Because every stage only ever adds a constraint the previous incumbent satisfies, the incumbent of the last stage that produced one is feasible for the original constraints, and that is what is published. A partially staged result **is** cacheable: it is exactly the promise the cache makes, and `objectiveValues` records per term how far the run got instead of implying proof it does not have.

- **What Optimized guarantees:** two independent, multi-worker, time-limited best-found runs cannot guarantee that PRI's priority value beats Time's and Time's makespan beats PRI's — either run may simply find a better incumbent for the other's primary term — so that cross-objective claim is struck everywhere. What is guaranteed instead is checkable and is what the product needs: **each stored variant's own primary term, measured on the materialised schedule in the real domain, is no worse than real Fast's value for that term.** Three mechanisms make that true rather than hoped for: the quantised baseline is supplied as a solution hint and as stage 1's upper bound so the search starts feasible and can only improve inside the quantised model; Lemma A makes the materialised result real-feasible; and the real-domain publication guard falls back to Fast's own schedule when quantisation loses more than the search won. A run that cannot beat Fast publishes Fast's value, which is a valid result rather than a failure.

- **Time quantisation and the quantised baseline (Sol r6 Critical 2):** the previous “integer whole workdays computed by the caller” rule was false and the fixed-point replacement was still unsatisfiable. `durationOf` returns `ASSUMED_SLICE_WORKDAYS` for `days === null` **without** dividing by `width`, and `days / width` otherwise **without** calling `snapWorkdays`; `snapWorkdays` only removes floating drift near an integer and deliberately preserves genuine fractions. Widths outside the divisors of 48 are legal — the API accepts every safe integer width 1–1000 and estimates are arbitrary finite non-negative numbers — so no fixed denominator makes every duration exact. Three serial slices with `days=1, width=5` are 0.2 workdays each and Fast finishes at 0.6 workdays = 28.8 units at `SOLVER_QUANTUM = 48`; rounding each duration up to 10 units needs 30. **Real Fast's value is therefore not a satisfiable upper bound for the quantised model, and the earlier plan's hint and stage-1 bound were infeasible on legal data.** The satisfiable policy has three parts, and each is a lemma with a test:
  1. **Round durations up, never down.** `durationUnits(s) = ceil(duration(s) × SOLVER_QUANTUM)`, with `duration(s)` computed by Fast's exact rule. The rounding per slice is recorded in the request. **Lemma A (real-feasibility):** because every quantised duration is ≥ its real duration and every start is an exact unit multiple, any solution feasible in the quantised model is feasible in the real domain — no predecessor, floor, assignee or pool constraint can be violated by materialising it. So quantisation costs optimality, never validity.
  2. **The bound and the hint come from the quantised baseline, not from real Fast.** `fastHint` and `baselineOffsets` are the **quantised Fast baseline**: Fast's own placement re-run through the same `schedule()` code path over the rounded durations, expressed in units. It is a feasible solution of exactly the model the solver receives, by construction, so the stage-1 upper bound `term ≤ baselineTerm` and the solution hint can never make a Fast-schedulable plan INFEASIBLE. `MOVEMENT` is measured against those integer baseline offsets, so it always has an integer representation.
  3. **A real-domain publication guard replaces the false guarantee.** Before storage the materialised optimized schedule is scored **in the real domain** against **real Fast's** value for that variant's own primary term (`PRIORITY` for PRI, `MAKESPAN` for Time). If the optimized value is worse — which quantisation alone can cause, as the width-5 case shows — the stored variant is **Fast's own materialised schedule**, tagged `publication: 'quantisation-floor'`. **`quantisation-floor` is a publication tag and never an `ObjectiveValue.status` (Sol r8 Critical 5, kimi r8 Important 2).** The earlier wording put it on `objectiveValues[primary].status`, which the stage-status matrix — the single authority for the wire schema and JSON codec — fixes at exactly `optimal | feasible | unknown`; no database `CHECK` is generated for either JSON-contained enum. It also mixed unit domains in one record: `value` is recomputed on the published offsets, but a floor row's published offsets are real Fast's real-domain schedule while `stageValue` and `bound` belong to the solver's quantised run over a _different_ schedule. So for a `publication: 'quantisation-floor'` row: `value` is recomputed **in the real domain on the stored Fast schedule** for all three terms — in **fractional workdays**, finite and not necessarily integral (Sol r12 Critical 1) — `stageValue` and `bound` are `null`, `status` is `'unknown'` (no stage produced this schedule), and the `value ≤ stageValue` relation is **not** checked — it is a within-stage relation and has no meaning across the two domains. For a `publication: 'solver'` row all four fields are present and the relation is checked exactly as the matrix says. That is a valid publishable result the design already permits (“a run that cannot beat Fast returns Fast's own value”), so the product guarantee below stays literally true and no valid plan is ever mislabelled `invalid-output` or `no-solution`.
     `notBeforeUnits`, `horizonUnits` and every returned offset are in the same units; Bun divides by `SOLVER_QUANTUM` before materialising, so what is stored is in the fractional workday unit Fast already uses. **The horizon is a real serial bound rather than the integer ceiling:** `horizonUnits = max(0, ...notBeforeUnits) + Σ durationUnits` — the zero identity is load-bearing, not tidiness: a plan with slices and an empty `notBefore` map is the default state of nearly every project, and an unseeded `max` over an empty set has no value, which is why `schedule.ts:2051` writes `Math.max(0, ...)` for the same shape — and every feasible schedule fits inside it because serialising every slice after the last floor is itself feasible. It is checked against `2^31 − 1` before spawn and fails with `horizon-overflow` rather than being sent. `SOLVER_QUANTUM` is covered by `SCHEDULER_CONTRACT_VERSION`. The gate carries a width-5 three-slice serial fixture proving the hint is feasible, `MOVEMENT` is defined, and the stored variant's primary term is no worse than real Fast's; the same fixture round-trips its floor row through SQLite and the real plan read, asserting that the stored schedule **is** Fast's, that every stored `value` is the real-domain term on it, that `stageValue` and `bound` are null, that `status` is inside the three-value matrix domain; and that `publication` reads `quantisation-floor`.

- **Canonical input:** the exact argument tuple of `schedule(rows, edges, slices, notBefore, poolSizes, reach, deadlines)`. Hashed: every `PlannedRow`'s `id`, `parentId`, `position`, `frozenNumber` and as-written `priority`, sorted by id; authored `{ predecessorId, successorId }` edges, sorted; the `slices` array **grouped by work item, groups ordered by work-item id, and each group's own order preserved as given** — the intra-item order is step precedence and carries meaning, the order _between_ groups does not and must not be hashed, because production `WorkItemRepo.listByProject` selects work items with no `ORDER BY` and `slicesOf` emits each group in that row order, so SQL is free to hand blue and green different global arrays for one unchanged project. Each slice carries `workItemId`, `stepId`, `days` (null distinct from 0), `personId`, `width` and the sorted set `poolIds: readonly string[]`. Then `notBefore` entries as whole days from day zero (so `project.startDate` is normalised away rather than hashed); `poolSizes` entries; `reach` from `project.dep_reach`; and `deadlines` entries as `[workItemId, deadlineOffset]` sorted by id, resolved by `deadlineOffsetOf` into whole workdays from day zero exactly as `notBefore` is, keyed by **as-authored** work item ids rather than the leaf expansion — the fold is derived, and hashing the expansion would hide a parent's deadline edit that binds no leaf today and binds one after a move, which is the same argument as-written `priority` already makes. A deadline is **not** a new cache-key dimension: it is inside the hash like every other input, and Objective, `contractVersion` and `budgetMs` remain the only key columns beside `(projectId, inputHash)`. Excluded: Engine, Objective, the toggle, the display variant, clock, acting user, and request sequence — nothing in `schedule()` reads them. Objective, `contractVersion` and `budgetMs` are separate key columns, not hash inputs. **`listByProject` deliberately does NOT acquire `ORDER BY work_item.id` in this change, and this sentence used to say it did.** The PR 203 review named that read as its second remedy and it is **withdrawn to TASK-260**, which owns the response-order contract, the sibling-uniqueness decision, the `(project_id, id)` index and the pre/post fixtures. The reason it cannot ride along here: for an existing project whose two siblings share a position and a one-slot team, ordering the read exchanges which sibling runs at days 0–2 and which at 2–4 — a deployment-visible date movement, and the one thing this change guarantees it does not do. Hash stability does not depend on it either way, which is the point of the paragraph above: canonicalization groups by work item and orders the groups itself, so the unchanged-hash proof is still built through the real adapter rather than by reordering `rows` in a fixture, and it holds over whatever order SQL returns.
- **Cache identity:** one SQLite table `optimized_schedule_cache` in the existing application database, declared in `apps/be-01/src/repository/schema.ts` with a forward migration under `apps/be-01/drizzle/`. Three companion tables ship in the same slice and carry `contractVersion` as a key column so co-existing releases never fence each other: `optimization_generation` keyed `(projectId, contractVersion)`, `solver_slot` keyed `(projectId, contractVersion, generation, objective, budgetMs)`, and `solver_queue` keyed `(projectId, contractVersion, objective, budgetMs)`. The cache's composite primary key is `(projectId, inputHash, objective, contractVersion, budgetMs)` → `generation`, `status` (`'ok' | 'failed'`), `resultJson` (NULL iff failed), `failureReason` (NULL iff ok), `createdAt`. A row satisfies a read iff `status='ok'` and every key column plus `generation` matches the project's current state. Integrity is declared in the schema, not assumed: `projectId` FK `ON DELETE CASCADE`, `CHECK (status IN ('ok','failed'))`, a CHECK tying `ok` to non-NULL `resultJson` + NULL `failureReason` and the inverse for `failed`, `CHECK (objective IN ('pri','time'))`, `CHECK (failure_reason IS NULL OR failure_reason IN ('timeout','invalid-output','no-solution','internal-error','oom','horizon-overflow','objective-overflow'))`, and read-time decoding that **leaves** an unparseable row in place and reports the variant `corrupt` rather than deleting it and treating it as a miss (Sol r7 Important 13). **Retention is two rules, because one was false (Sol r6 Minor 15).** Generation changes only when `inputHash` changes, so raising `budgetMs` or deploying a new `contractVersion` reuses the generation and inserts a _different_ composite-key row — every superseded budget and version pair stayed part of the current generation and “only the latest pair is retained” was untrue. So: (1) allocating a new generation deletes every row of that project for that contract version in the same transaction, which is what makes an undo back to a previous hash a miss that re-solves with Fast visible throughout; and (2) when a new outcome commits, the same transaction keeps the `MAX_LIVE_BUDGETS = 2` most recently written budgets for `(projectId, objective, contractVersion, inputHash)` and deletes the rest — a bound rather than an exclusion, because deleting every differing-budget row let two releases reading different budgets evict each other for ever (Sol r7 Important 9). Reads are keyed by the current budget, so nothing readable is lost. The resulting ceiling is exact and is the one the Risks section must claim verbatim: **at most `MAX_LIVE_BUDGETS` = 2 rows per project per objective per live contract version, so 4 outcome rows per project per live contract version**, with live contract versions bounded by the `GENERATION_RETENTION_DAYS = 30` retirement rule above. **`apps/be-01/drizzle/**` is a prod-mode path, so every slice that lands a migration ships as a reviewed PR and is not self-merged.\*\*
- **Contract version:** `contractVersion = "<SCHEDULER_CONTRACT_VERSION>+<solverVersion>"`. `solverVersion` alone was unsound, because durations, the leaf expansion and `baselineOffsets` are produced by Bun/domain code that the Python package version does not describe. `SCHEDULER_CONTRACT_VERSION` is an exported constant in `libs/domain`, bumped by any change to Fast semantics, `ASSUMED_SLICE_WORKDAYS`, `snapWorkdays`, reach or numbering semantics, resource tie-breaks, the canonicalizer, or the duration rule — and guarded by keying the Fast golden corpus on it, so an unbumped Fast change fails the corpus rather than silently serving stale rows.
- **Generations are per contract version, cancellation is its own epoch, and drain closure is durable (Sol r6 Criticals 3–4, Important 10; Sol r11 Critical 1):** the single pair of project columns could not survive blue/green releases sharing one database. The current identity therefore lives in `optimization_generation`, keyed **`(projectId, contractVersion)`** → `generation`, `inputHash`, `cancelEpoch`, `admissionState ('open' | 'draining')`, `updatedAt`. Each release owns its row; cache, slot, and queue keys carry `contractVersion`; process ceilings remain global across both. A nullable internal `project.optimizationDeletePendingAt` is the project-wide deletion fence. Deletion and retirement use **two-phase cancel-and-drain** through named `beginOptimizationDrain(projectId, contractVersion?)` and `finishOptimizationDrain(projectId, contractVersion?)` seams. Begin is one transaction: retirement sets the targeted generation to `draining`; project deletion first sets `optimizationDeletePendingAt` and marks every generation for that project `draining`; both paths advance `cancelEpoch`, stamp `cancel_requested_at` on affected slot rows, and delete affected queue rows. Admission and dequeue both require `admissionState='open'` and no project deletion marker. A delete-pending project is hidden from ordinary reads and writes, but its physical row stays until every affected slot is released or passes `admittedDeadlineAt`, so the rows continue to count live processes. Finish transactionally requires the durable closed state and zero affected slots before deleting the generation or project row. A 30-day untouched or deploy-retired generation enters this same protocol.
  **Completion is not owned by the initiator (Sol r12 Critical 3).** Making the closure durable fixed the race and created a wedge: only the initiating request was required to call `finish`, so a crash after committing `draining`/`optimizationDeletePendingAt` left the project hidden, admission closed and the physical rows undeletable for ever — and no later admission could sweep it, because admission is precisely what a draining project rejects. Two paths therefore run `finishOptimizationDrain`, both idempotent and both safe to race: **(a) opportunistic** — every slot release and every reclaim sweep, in the _same transaction_ that removes the last affected row, re-reads the durable marker and finishes the drain when zero affected slots remain; **(b) reconciliation** — `reconcileOptimizationDrains()` runs on coordinator startup and every `DRAIN_RECONCILE_INTERVAL_MS = 60000`, scans generations in `admissionState='draining'` and projects carrying `optimizationDeletePendingAt`, reclaims any affected slot already past its stored `admittedDeadlineAt`, and finishes those with none left. Both call the _same_ transactional `finish`, whose precondition is unchanged — the durable closed state still holds and zero affected slot rows exist — so concurrent reconcilers are safe by that precondition rather than by a lock, and the loser simply observes the generation or project row already gone; `finish` is a no-op on an absent target. Neither path ever reopens admission: a begun drain terminates only in deletion or retirement. This closes the zero-slot-observation race across coordinators; `ON DELETE CASCADE` remains a backstop after drain, never the mechanism that frees a live child's slot.
  Allocation within one release's row is one compare-and-swap transaction: read `(generation, inputHash)`; if the stored hash equals H, reuse the generation unchanged, so a backend restart on an unchanged plan allocates nothing; otherwise `UPDATE … SET input_hash = :H, generation = :seen + 1 WHERE project_id = :p AND contract_version = :c AND generation = :seen`, and in the same transaction delete the older generation's **cache and queue** rows. A losing writer retries and observes the winner's H rather than allocating a second generation for one input. This is what makes cold-read coalescing and “exactly one child per objective” implementable across processes, and it fences the H1→H2→undo-to-H1 ABA sequence, a cancelled child stamping `failed` over a live `ok`, and two writers of one key.
  **Slot rows are deliberately not deleted by allocation.** Deleting them freed the count before the corresponding processes were proved dead, so the next generation saw free rows while the old pair was still terminating and repeated edits could leave six or more real children running while SQLite counted two — falsifying the settled 4/16 ceilings outright. Allocation instead sets `cancel_requested_at` on the previous generation's slot rows and **leaves them counted until their owner releases them or `now > admittedDeadlineAt` reclaims them**, so the row count is an upper bound on live children at every instant.
  **Turning the toggle OFF advances a cancellation epoch, not the generation.** The toggle is excluded from `inputHash` by design, so an OFF transition cannot advance a generation that allocation is required to reuse for an unchanged hash — those two rules could not both be implemented, and the earlier tasks asked for both. OFF is one transaction that sets `optimization_enabled = 0`, increments `cancelEpoch` **for every contract version of that project**, sets `cancel_requested_at` on all of that project's slot rows and deletes its queue rows. Every spawn carries `(generation, cancelEpoch, attemptToken)`, and **every **worker-owned** result, failure and eviction write is conditional on the generation still being current, the cancel epoch being unchanged, `optimization_enabled` still being 1, and the writer's own `attemptToken` still matching its live slot row**, in the same transaction as its event. That predicate is scoped rather than universal (Sol r10 Important 9): allocation eviction is authorized by the winning generation CAS, OFF cleanup by the `cancelEpoch` increment in its own transaction, and deletion/retirement eviction by the cancel-and-drain protocol — none of the three has a child token to present, and requiring one would make all three impossible — so a child that outlives a local cancellation, or belongs to the other backend entirely, can neither store nor broadcast. A local process handle cancels only local children and `PR_SET_PDEATHSIG` is irrelevant when the other coordinator is still alive, so the durable channel is the slot row: an owner's heartbeat reads `cancel_requested_at` and the project's epoch on the same round trip and kills its child when either moved, bounding real termination by one heartbeat interval. The gate carries the two-coordinator test: blue owns both children, green PATCHes the toggle OFF, both real children exit, and neither can store or emit an outcome.

- **The cached row stores a result, not a schedule (Sol r7 Critical 6):** `objectiveValues` is what records how far a partially staged run got, and the real-domain publication guard has to persist `publication: 'quantisation-floor'` with `status: 'unknown'` and null `stageValue`/`bound` on the primary term — `quantisation-floor` is a `publication` value and never a `status` value, and putting it back into `status` is a standing watched red — but the cache had only `scheduleJson`, and `encodeSchedule` is a codec for `Schedule`, which `libs/domain/src/schedule.ts` confirms carries no objective metadata at all.   **Shape is shared; the numeric domain is not, and both are named (Sol r12 Critical 1).** The earlier text said the stored shape is identical to the wire shape and then imposed the wire's rule — every non-null objective number a non-negative safe integer — on the one row whose `value` the floor guard is _required_ to recompute in the real domain.   - `publication: 'solver'` — `value`, `stageValue` and `bound` are in **quantised solver units** (integer multiples of `1 / SOLVER_QUANTUM` workdays, the wire's own unit); each non-null number must be a **non-negative safe integer**, and anything else fails decoding, exactly as on the wire.
  - `publication: 'quantisation-floor'` — each `value` is the term recomputed in the **real domain**, expressed in **fractional workdays**, the unit the stored schedule's own offsets already use; each must be a **finite non-negative `number` that need not be an integer**, with `NaN`, ±`Infinity` and negatives failing decoding and the safe-integer check deliberately **not** applied. `stageValue` and `bound` are null, so no quantised number appears in a floor row at all and the two domains never meet inside one record.
    **Comparison semantics for the real domain.** A real term is compared only against another term from the same scorer: `scoreReal(schedule)` returns `(MAKESPAN, PRIORITY, MOVEMENT)` accumulated over slices in canonical order, so the publication guard's two sides — the materialised optimized schedule and real Fast's — are summed in the same order over the same terms and compared with plain IEEE-754 `>` on `number`, no epsilon and no rounding; “strictly worse” is exactly `scoreReal(optimized)[primary] > scoreReal(fast)[primary]`. A stored real value is **never** compared against a quantised one — that is why the `value ≤ stageValue` relation is skipped on a floor row and why the comparison indicator reads `publication` rather than inferring a win from the numbers. JSON round-trips a finite double exactly, so the reload assertion is bit-equality against `scoreReal` re-run on the reloaded Fast schedule, never against a decimal literal: `0.2 + 0.2 + 0.2 !== 0.6` in IEEE-754, and asserting the literal would be a flake rather than a check. **Where each of those is enforced is a boundary, not a blanket (Sol r10 Important 11):** `publication` and every per-term `status` live _inside_ `resultJson`, so no database column `CHECK` can cover them; SQL `CHECK`s cover the scalar columns only (cache `status`, `objective`, `failureReason`). `decodeOptimizedResult` is the sole validator of the JSON-contained `publication` and per-term `status`. No blanket JSON-validity `CHECK` is added, because malformed `resultJson` must still be _storable_ so that a read can surface it as `corrupt`. `publication` is stored rather than inferred, because a `quantisation-floor` row is materially Fast's schedule and the comparison indicator must not present it as a solver win. Nothing else moves into columns: the values are read only with the row that carries them, so normalising them would buy no query and cost a join. **Proven by** a partially staged row (`status: 'unknown'` on the last term) and a `quantisation-floor` row each surviving a round trip through SQLite and the real plan read with every field intact, plus the negative where `resultJson` holds a bare `encodeSchedule` output and `decodeOptimizedResult` throws naming the missing `dtoVersion`.

- **Cache DTO and codec (Sol r6 Important 8):** `scheduleJson` was called “the serialised full `Schedule`” with no shape and no codec, and `Schedule` carries `Map<string, ScheduledSlice>` and `Map<string, Scheduled>`, which `JSON.stringify` renders as `{}` — an implementation could pass every type-level materialiser test and store a row that reloads as an empty plan. The stored value is therefore a versioned DTO with explicit functions: `CACHE_DTO_VERSION`, `encodeSchedule(schedule)` and `decodeSchedule(json)` in `libs/domain`. Both maps become **arrays of entries sorted by key** (`slices: [{ key, …ScheduledSlice }]`, `workItems: [{ id, …Scheduled }]`); `waitingForPerson`, `waitingForCapacity` and `eventsVisited` are stored so the round trip is total and the read path invents nothing. `decodeSchedule` enforces the invariants and throws naming the defect: `dtoVersion` known, no duplicate key, every `slices` key equal to its entry's own `sliceKey`, and `workItems` covering exactly the projected ids. The gate proves a **non-empty** round trip through SQLite and through the real plan read, plus malformed-key, duplicate-key and missing-projection negatives.
  **A decode failure is surfaced, not swallowed (Sol r7 Important 13).** The earlier read path deleted a malformed row and treated it as a miss, which contradicted the decoder throwing and, worse, contradicted this repository's AGENTS.md R5 rule that malformed trusted data throws rather than becoming a default — and it silently converted corruption into a **read-triggered solve**, which is the timer retry Dany rejected arriving through the cache instead of the clock. The row is therefore **left in place** and the variant reads as a sixth state, `corrupt`, carrying the decoder's message. The UI shows the same non-intrusive `Optimization unavailable · Retry`, so a user is never stranded, but the transition is explicit and manual: Retry overwrites the row through the ordinary admission path, and until then the bad row survives for diagnosis rather than being destroyed by the process that found it. `corrupt` never satisfies a read and never auto-spawns, exactly like `failed`. **Proven by** writing a truncated and a wrong-`dtoVersion` `resultJson` directly and reading through the production path: the row survives, the payload reads `corrupt` with the decoder's reason, ten reads spawn nothing, and Retry produces exactly one child.

- **Plan-read DTO and the Retry endpoint (Sol r6 Critical 5):** the plan added settings columns and cached rows but never said how `WorkItemService.tree` selects a variant into its existing fields, and no read could tell a freshly loaded client “pending” from “failed” — a failure event can move a client already connected, but it cannot reconstruct an initial page load. `tree()` therefore returns one additional `optimization` block beside the existing `workItems`, `slices` and the two wait counts: `{ enabled, engine, objective, inputHash, generation, contractVersion, budgetMs, displayed, variants: { pri, time }, comparison }`. `displayed` is `'fast' | 'pri' | 'time'` and names which schedule the existing arrays hold; `comparison` is `{ deltaDays, sameOrder }` and is present exactly when `displayed !== 'fast'`. Each `VariantState` is a tagged union of **seven** members: `ready` (an `ok` row for the current key), `pending` (no row and a live entry for the full key), `retrying` (a `failed` **or `corrupt`** row and a live entry for the full key), `failed` (a `failed` row and no live entry, carrying `reason`), `corrupt` (an `ok` row whose `resultJson` fails to decode, and no live entry, carrying the decoder's message — no live entry is required to reach it), `plan-infeasible` (a `plan-infeasible` row and no live entry, carrying every offending work item with its **effective** deadline, the owning id and the id the constraint fell on), or `idle` (no row and no live entry, which is what the toggle being OFF looks like). `corrupt` renders the same `Optimization unavailable · Retry` control as `failed`; the two differ in provenance and in nothing the user sees. `plan-infeasible` renders `Plan infeasible · N work item deadlines` and **no** Retry control: a stage-1 `INFEASIBLE` on a well-formed model is the engine working correctly, the answer is a deterministic function of the input, and only a new input hash can change it (`openspec/changes/work-item-deadline/design.md` §3.3). It is not on the `failed`/`invalid-output` path, and a _later_-stage `INFEASIBLE` stays `invalid-output` — it carries no offending-item certificate and is impossible on a correct engine. **This union is the one authority** — the round-7 disposition added `corrupt` to spec.md and left this list, `tasks.md` 7.10 and the UI test list at five members (Sol r8 Critical 6), which is the same cross-artifact divergence rounds 2–4 each found. **Selection rule:** the arrays hold Fast when the toggle is OFF, when `engine === 'fast'`, or when the selected variant is not `ready`; otherwise they hold the materialised selected variant. That makes a cold reload renderable in every state without a second request.
  The `retrying` state is also what resolves the failed-row dilemma: the marker is **never deleted before its replacement commits**, so every read during a retry would otherwise still render “unavailable”, while deleting it would make the next read auto-spawn — the timer retry Dany rejected. The distinct in-flight state is the live slot or queue row, not the absence of the marker. **Retry is a real route:** `POST /api/projects/:projectId/optimization/retry` with body `{ objective, inputHash }`, under the same project-write authorization as the settings PATCH. It runs the ordinary admission transaction, so two concurrent Retries produce one child. The codes are decided in **one stated evaluation order**, because listing them without one made `pending` ambiguous (kimi r10 Important 2): (1) `409 { code: 'stale-input-hash', currentInputHash }` when the body's hash is not current; (2) **then** `409 { code: 'not-retryable', state }` unless the current row is `failed` or `corrupt` — which is how `ready`, `pending` and `idle` are answered, `pending` having no row at all; (3) **then** `409 { code: 'already-running' }` when a live entry exists for **the full cache key including `budgetMs`**, which is exactly the `retrying` state and the double-posted Retry; (4) otherwise `202 { state: 'retrying', generation, inputHash }`. Retryability is tested before the live-entry check on purpose: the reverse order returns `already-running` for `pending`, whose own definition guarantees a live entry, and the gate sentence below requires `not-retryable` there. **Retry accepts a `failed` row or a `corrupt` one (Sol r8 Critical 6):** the codec requirement promises an explicit Retry overwrites a corrupt row and is the only recovery path that exists for it, but the previous `not-failed` guard tested for a failure marker and a corrupt row is a `status='ok'` row, so the only authorized recovery action was forbidden by the endpoint that offers it. The gate proves the corrupt path end to end: two concurrent Retries on one corrupt row coalesce to a single child and both read `retrying`, the bad row survives untouched until the replacement transaction commits, it is then overwritten exactly once, and a Retry against a `ready`, `pending` or `idle` variant returns `not-retryable` naming the state. The gate proves a reload through the **real controller payload** in the cold, queued, retrying, failed, **corrupt**, partial-success and full-hit states.
- **Failure:** fail-closed and governed by one state machine. A failure writes exactly one `status='failed'` marker row with a `failureReason` (`timeout | invalid-output | no-solution | internal-error | oom | horizon-overflow | objective-overflow`); Fast stays visible; failure is variant-specific. That row never satisfies a read, and it **does** suppress an automatic re-spawn for its exact key — a later read and a same-hash edit both launch nothing, because a read is a timer retry in disguise — while never blocking an explicit Retry (which overwrites it) or the fresh generation a new hash starts. A cancelled run writes no row at all.
- **Events:** a newly stored `ok` row and its durable `event_log` record are written in **one SQLite transaction**, and the broadcaster pushes from the committed record. A newly written `failed` marker row does the same through a second, non-result event **`schedule_optimization_failed`** — without it the read returns Fast while children run, success later emits `schedule_optimized`, and a failure emits nothing, so a client already on screen would sit at `Optimizing…` for ever and the manual Retry control would never appear; when both variants fail no connected client would have any reason to read the marker at all, and when one succeeds its unrelated success event would reveal the other failure by race. This does not disturb the settled rule that a cache **hit** broadcasts nothing: a hit is not a new outcome, and a newly written `failed` row is. The failure event carries no schedule and triggers no variant refetch — it flips that variant to `Optimization unavailable · Retry`. Both event payloads are `(projectId, generation, inputHash, objective, contractVersion, budgetMs)`, the failure one adding `failureReason`; **`budgetMs` is in the identity because it is a cache-key column** — raising the budget changes neither the hash nor the generation, so without it a larger-budget result would announce itself under the smaller-budget result's identity and a client holding that identity would ignore the only notice that should move it. **The delivery guarantee is narrowed to what the stack can keep:** one durable replay record per new outcome, plus one best-effort post-commit push. `event_log` is a replay buffer consulted on resume, not a dispatched-and-acknowledged outbox, and the process can die after commit and before the push, so “delivered at least once” over a live socket was false. The no-outbox constraint stands. The seam is named rather than assumed, because today `EventLogRepo.recordEvent` opens its own transaction and `GatewayBroadcaster.publish` both records and pushes: `recordEventIn(tx, subscription, message, createdAt)` writes inside the caller's transaction, and `pushRecorded(subscription, recorded, event)` buffers and pushes an already-recorded sequence without recording it twice; `publish` becomes those two calls and keeps its behaviour.
- **Resource ceilings and slot fencing (Sol r6 Critical 4):** 4 solver processes per project, 16 global (Dany 2026-09-02), enforced in SQLite rather than coordinator memory — blue and green coexist against one database file and two in-memory coordinators would each admit their own sixteen. `solver_slot` is keyed **`(projectId, contractVersion, generation, objective, budgetMs)`** and holds `ownerId`, `attemptToken`, `lifecycle` (`'starting' | 'running'`), `pid` (NULL while `starting`), `startedAt`, `heartbeatAt`, `cancelRequestedAt` and `admittedDeadlineAt`. **`budgetMs` belongs to the identity because it belongs to the cache key (Sol r8 Critical 2, kimi r8 Important 3).** `MAX_LIVE_BUDGETS = 2` exists precisely because blue and green may read 60000 and 120000 under one `contractVersion`; without the column a 60 s and a 120 s solve for one objective collided as if they were the same work, the plan-read rule “a live slot or queue entry **for that key**” could not be evaluated at all because the live rows did not carry the full key, and a 120 s child in flight beside a 60 s `failed` marker made the 60 s variant read `retrying` when nothing had retried it. Every liveness lookup, the `pending`/`retrying` derivation and Retry's `already-running` check now match the **full** key. The 4-per-project and 16-global ceilings are unchanged and still count **every** unreleased row regardless of budget, because they bound processes rather than keys. Admission is one transaction that reclaims slots whose stored `admittedDeadlineAt` has passed, refuses at 4 per project and 16 global counting **every** unreleased row including those already asked to cancel, then inserts with a freshly minted 128-bit `attemptToken`.
  **The token is the fence, and it is checked on every subsequent write.** Heartbeat, release, the cache/failure write and the event write all carry `WHERE attempt_token = :token`; a superseded owner's statement matches zero rows and it aborts rather than refreshing or deleting a replacement slot, and the cache write is a conditional insert asserting its own live slot row rather than a blind upsert — so two nondeterministic results can no longer overwrite each other or emit two outcome records for one key. Reclamation mints a **new** token for the replacement, which is what makes the old owner's late heartbeat, release and write all fail.
  **Admission, spawn and arming are one lifecycle protocol with a `starting` state (Sol r12 Critical 2).** Reserving the slot before spawning is what makes the row count bound processes, but the PID is unknown at reservation time, the request schema carries neither a stamped deadline nor a start instant, and the solver may not read a clock — so nothing tied the reserved row to the process it authorised. A coordinator or OS pause longer than `SLOT_RECLAIM_MARGIN_MS` between admission and spawn let the row be reclaimed and a replacement admitted, after which the delayed owner woke and spawned a _second_ live child for one slot; and a child arming `budget + 5000` from whenever it happened to start carried a later alarm than the row that authorised it. The protocol is therefore explicit end to end, and `solver_slot` gains a `lifecycle` column (`'starting' | 'running'`):
  1. **Reserve.** Admission inserts the row `lifecycle='starting'` with `pid` NULL, a fresh `attemptToken`, `startedAt = now`, and the absolute `childDeadlineAt`/`admittedDeadlineAt` pair computed once from the admitting coordinator's own `budgetMs`. A `starting` row counts against 4 and 16 exactly like a `running` one — it _is_ the reservation — and is reclaimed by the same `now > admittedDeadlineAt` rule.
  2. **Spawn.** The coordinator opens one authenticated connection to the host-owned supervisor described in `supervisor-amendment.md`. The supervisor derives caller identity with `SO_PEERCRED`, selects the host mapping, applies host-owned limits, and creates/attaches/starts one hardened managed container running `wbs-solver-launcher`. The token and `childDeadlineAt` stay argv metadata, never request fields. The launcher blocks before reading the request. CP-SAT's time limit remains the partial-result path; a transient systemd user timer owned by the host kills the exact container at `childDeadlineAt` even if the supervisor process restarts.
  3. **Bind.** After create/attach/start, the supervisor returns the container init PID. The coordinator CASes `UPDATE solver_slot SET pid = :pid, lifecycle = 'running' WHERE <key> AND attempt_token = :token AND lifecycle = 'starting'`. One row means the supervisor may forward `bound` plus the exact request; zero rows means `abort` and ordered container termination. Abort, closed connection, `BIND_TIMEOUT_MS = 5000`, or `now >= childDeadlineAt` starts no solve. Container removal happens only after kill, wait, and inspect preserve terminal evidence.
  4. **Fence.** Every later statement keeps `WHERE attempt_token = :token`, so a reclaimed owner's heartbeat, release and outcome write still match zero rows.
     **The ceiling this establishes:** live managed solver containers never exceed all unreleased slot rows (`starting` plus `running`), hence at most 4 per project and 16 fleet-wide. Solve-start state begins only after the bind CAS and therefore never exceeds `running` rows. The exit side rests on the persistent host systemd timer's `docker kill` at `childDeadlineAt`, not on child timeliness or the supervisor process staying alive. Kill, wait, and inspect complete before removal; `admittedDeadlineAt` remains a full margin later so SQLite never re-admits capacity while a managed container may still run.
     **Reclamation never authorises a replacement while the old child may still be running.** `childDeadlineAt = startedAt + budgetMs + 5000` is armed in CP-SAT and in a transient host systemd timer; `admittedDeadlineAt = childDeadlineAt + SLOT_RECLAIM_MARGIN_MS` is stamped once in SQLite and used only for `now > admittedDeadlineAt` reclaim. Coordinator disconnect makes the supervisor kill its exact container; supervisor restart leaves the timer armed and its pre-listen sweep clears managed orphans. `solver_queue` keeps its full key and deterministic order, persists `admittedCancelEpoch`, and applies the existing generation, admission-state, epoch, toggle, and deletion predicates.

- **The empty project is a defined case, and it bypasses both solvers (Sol r7 Important 12):** a project with no slices is legal — `schedule` handles it explicitly with `projectFinish = Math.max(0, ...placedFinishes)` and empty maps — but `MAKESPAN = max finish` has no empty-set identity, so it was undefined on a plan the product allows. (`horizonUnits` is a separate case and is **not** an argument for the short-circuit: its `notBeforeUnits` max is seeded with zero, so it is defined for every plan including one with slices and no manual floors, which is the common case — kimi r10 Minor 4. Its `Σ durationUnits` term is likewise zero on an empty plan.) Rather than define `max ∅ = 0` and carry the special case through CP-SAT, the coordinator **short-circuits**: a canonical input with zero slices is never sent to a solver, allocates no slot, writes no cache row and emits no event; the plan read returns Fast (which is already correct and empty) with every variant `idle`, exactly as the toggle being OFF looks. The same short-circuit covers a plan whose slices all carry `days: 0`, where every duration is zero and the search has nothing to order. **Proven by** a cold read with optimization ON and zero work items: no spawn on the injected spawner, no row, no event, and a renderable payload — and the same after adding then deleting the only work item, which is the transition that would otherwise leave a stale row.

- **Budget:** one config value `solverBudgetMs`, default 60000 (Dany's >=60s floor), child killed at `solverBudgetMs + 5000`. It **is** a cache-key column, because a larger budget can find a better feasible result and an operator who raises it must not keep being served the smaller-budget answer. The cached promise is exactly "the best result found for this input, this contract, this objective, at this budget". **But budget is not a generation or slot namespace, and the earlier retention rule turned that into a livelock (Sol r7 Important 9):** a config change is not a code change, so blue and green can read 60000 and 120000 under one `contractVersion`, and "a committing outcome deletes every other row whose `(inputHash, budgetMs)` differs" made each release delete the other's row the moment it stored, so the two alternated solves on an unchanged plan and could hold the 4/16 ceilings busy indefinitely. The per-contract generation table fixes this for code versions and cannot fix it for budgets. **Retention rule 2 is therefore bounded rather than exclusive:** a committing outcome keeps the `MAX_LIVE_BUDGETS = 2` most recently written budgets for `(projectId, objective, contractVersion, inputHash)` and deletes the rest; rule 1 (a new generation clears that contract version's older-generation rows) is unchanged and is what keeps the total finite. Two co-existing releases therefore each keep their own row, neither re-solves for an unchanged plan, and the bound becomes **at most two rows per project per objective per live contract version**. A third simultaneous budget is a deployment nobody runs; if it happens, the least recently written row is evicted and that release re-solves once rather than for ever. **Proven by** a two-release fixture reading different budgets against one file: each stores once, each then hits its own row, and the injected spawner sees exactly two solves across ten alternating reads.
- **Restart and orphans:** no in-flight child is resumed and no in-memory queue is rebuilt; durable queue entries retain the ordinary dequeue predicates. Coordinator disconnect makes the host supervisor kill that connection's exact managed container. The restart-always supervisor leaves each systemd deadline timer armed and kills, waits, inspects, and removes managed orphans before reopening its socket. A coordinator that loses the socket without terminal evidence keeps the slot counted through the deadline margin. SQLite reclaims only after `admittedDeadlineAt`, never from a missed heartbeat.
- **Stored-enum boundary (Sol r10 Important 11; Sol r11 Important 5):** the rule splits by _where the enum lives_. Every enum in its **own scalar column** gets both a database `CHECK` and an explicit read-time validator: cache status/objective/failure reason, project Engine/Objective, generation `admissionState`, and `solver_slot.lifecycle` (`'starting' | 'running'`, added by Sol r12 Critical 2 and omitted from both enumerations until Fable r14 Important 2 — the blanket rule covered it, its own instantiating list did not, and an implementer following the list would build every validator but that one), and — the same defect one column further on, found by Fable r18 Important 1 — `solver_slot.objective` and `solver_queue.objective`, which are the same `'pri' | 'time'` enum in their own scalar column and in their table's primary key, and which every instantiating list omitted while the blanket sentence above covered them. They reuse `isObjective`, so this adds two validated _columns_ and no new validator: a stored enum is a column, not a type, and validating the cache's `objective` never covered its siblings. The dequeue is why it matters — it reads `solver_queue.objective` into the typed spawn identity, so a corrupted row launches a garbage-objective solve whose failed-marker write then violates the cache's own `CHECK`, leaving that key with no marker and no `schedule_optimization_failed` event. Every enum **inside `resultJson`** — `publication` and each per-term `status` — gets codec validation only, with no JSON-validity or JSON-extraction `CHECK`; malformed JSON must remain storable so a read can surface it as `corrupt`. The scalar validators mirror `toProject`: they throw naming the column and stored value rather than cast or default. The optimization boolean has `CHECK (optimization_enabled IN (0,1))`; `optimizationDeletePendingAt` is a nullable timestamp, not an enum. Negative tests inject an unknown value for every scalar enum and the boolean on the production read path, plus unknown JSON-contained enums through `decodeOptimizedResult`.
- **Project settings:** the toggle, Engine and Objective are project-scoped persisted columns, not view state. An additive migration adds `optimization_enabled` (default false, which is what makes OFF-by-default true for existing rows), `schedule_engine` (default `'fast'`) and `schedule_objective` (default `'pri'`), with repository mapping, a PATCH contract under the existing project-write authorization, the three settings in the read payload, and a new `project_settings_changed` variant on `ProjectEvent` emitted by `ProjectService.update`. The generation counter, the input hash and the cancel epoch deliberately do **not** live here: they are per contract version (see Generations), so they live in the `optimization_generation` table that slice 3 creates rather than on the project row. This is a **second prod-mode path**.
- **“Same order” — the exact comparison relation:** the indicator's four sentences (“Same deadline + same order”, “Same deadline + reordered”, and their earlier/later pairs) require a defined order, and map or array iteration order is not one. `sameOrder(a, b)` holds iff for **every** pair of slices `(s, t)` present in both, `sign(startA(s) − startA(t)) === sign(startB(s) − startB(t))`, compared **in the real fractional-workday domain on the two materialised schedules**, not in quantised units — real Fast's starts need not lie on the unit grid, so quantised comparison could label a pair reordered purely by rounding. That is a strict weak ordering by start: it is blind to a uniform shift of the whole plan, blind to iteration order, and it treats ties as first-class — a tie broken and a tie created are both “reordered”, which is the honest answer, since two slices that used to start together and now do not have visibly changed the plan. Zero-duration slices participate by start like any other. The relation is computed **server-side on the materialised schedules** and shipped as one boolean beside the day-count delta, so client and server cannot label the same pair differently.
- **The process ceiling is not a resource ceiling on its own:** production requests 2 search workers and 512 MiB per solve; the host supervisor independently caps those values, 128 PIDs per child, and 16 live managed containers. Docker memory plus equal memory-swap is the RSS authority; `RLIMIT_AS` is only a loose address-space backstop. Docker `OOMKilled=true` alone classifies a generic native failure as `oom`; the persistent deadline-timer kill is `timeout`; another non-zero exit is `internal-error`. The fleet obligation remains 32 CP-SAT search workers and about 8 GiB solver RSS at the full 16.
- **Determinism:** production runs multi-worker under a wall-clock budget and is explicitly not required to be reproducible; one result is stored and every collaborator refetches that row, so all clients converge. Reproducibility is asserted only under a pinned test configuration (`num_search_workers=1`, fixed `random_seed`, deterministic time limit).

- **Migrations ship with their rollback:** AGENTS.md mandates a `down.sql` beside every `migration.sql`, and both prod-mode slices previously asked only for a “forward migration”. Each of slices 3 and 3b explicitly creates its own `down.sql` and proves rollback-then-re-apply against the applied set; without it migration lint and `readMigrationFolders` refuse at the gate and an aborted blue/green deploy cannot return.
- **Packaging is part of the change, not a consequence of it:** creating the `wbs-solver` package and running its suite standalone can be green while every deployed solve fails on an absent executable. The Dagger/image path installs the pinned Python runtime and the locked OR-Tools environment, copies the package and **both its console scripts** into the be-01 runtime, exposes the installed version to the coordinator as the `solverVersion` half of `contractVersion`, and an ordered slice (5.11) proves a spawn **from the built image** through the production launcher path plus **two** negatives — the package absent, and the launcher absent from an image whose solve-entrypoint smoke test still passes. The Python suite gets its own Nx target wired into the gate.

## Risks / Trade-offs

- **New language in the stack (Python):** the deploy image must carry a pinned Python runtime plus OR-Tools. Mitigated by isolating the solver behind a one-line stdin/stdout contract and versioning the package into the cache key.
- **Two concurrent solves per edit:** CPU cost. Mitigated by the OFF-by-default toggle, debounce, cancellation, and the 4/16 ceilings.
- **SQLite growth:** the retention rules above bound this at **`MAX_LIVE_BUDGETS` (2) budgets × 2 objectives = 4 outcome rows per project per live contract version**, with live contract versions themselves bounded by the `GENERATION_RETENTION_DAYS = 30` retirement rule. **This paragraph previously said two rows total and that superseded budget rows are deleted when a replacement commits (Sol r8 Important 8)** — that is the exclusive rule whose cross-release eviction livelock the Budget decision removed, and contract versions are retired on age or deploy marking rather than replaced on commit. Rule 2 is a bound, not an exclusion. The earlier “only the latest pair” claim ignored budget and contract changes, which reuse the generation.
- **Best-found semantics:** a host-dependent solve could surface differing "optimal" dates; the exact input hash plus the reported day-count comparison forces like-for-like reads, and storing exactly one result per key means collaborators never disagree even though a re-solve might have found other offsets.
- **Two prod-mode migrations inside a dev-mode item:** the cache/generation/slot/queue tables **plus the internal `project.optimization_delete_pending_at` fence**, and separately the three user-facing project-settings columns (`optimization_enabled`, `schedule_engine`, `schedule_objective`), are the prod-mode paths here. **The fence column belongs to the first slice, not the second (Sol r12 Important 5):** slice 3's drain implementation and its two-coordinator process test read it, and the two slices ship as separate reviewed PRs, so creating it in slice 3b left slice 3 unimplementable against its own declared schema. Each slice's `down.sql` enumerates exactly what that slice added — the **four** tables `optimized_schedule_cache`, `optimization_generation`, `solver_slot`, `solver_queue` and the fence for slice 3, the three settings columns for slice 3b (Fable r14 Important 1: "three companion tables" beside the cache is four in total, and both enumerations undercounted). Each is isolated into its own slice (tasks.md slices 3 and 3b) so the rest of the change stays dev-mode and only those slices carry the reviewed-PR obligation, and each slice creates every column its own code and tests read.
- **Cross-process coordination in SQLite:** admission and generation allocation become contended write transactions on the same database as the application. Mitigated by keeping each transaction to a few indexed row reads and one insert, and by the 5-second slot heartbeat being an `UPDATE` on a primary-key hit.
