## Context

Preparation inspected `repository/index.ts`, `saved-plan-ports.ts`, the four current shared kits, both source registrations, the memory fixtures/allowlist and `core-lib-extraction` C6 on 2026-09-08. This design is documentation, not an executed certification. Implementation follows core extraction and uses its final source ports rather than copying application-local signatures.

The current `TransactionalStores` has seventeen fields; `users` combines UserStore and OidcIdentityStore. HistoryStores adds savedPlans and savedPlanCapture. Existing kits cover steps, estimates, directory and eventLog, with one memory exclusion: estimates.set:unknown_step. Comments identify actuals/measures/progress missing-step behavior as the same lag, but no exclusion exists until those cases exist. The current report.ran is filled at declaration, before the test body. The current memory source also wires subtree dependencies and journal/history independently; core C6 owns promotion to one state, and these new kits must observe that integration rather than certify the old disconnected fixtures.

## Goals / Non-Goals

Provide executable, capability-specific evidence for every store family, with a closed inventory and proved checks. Preserve valid memory exclusions without promising parity for unoffered behavior. This change does not implement absent features, change source semantics or treat a declared/skipped test as a passing one.

## Decisions

### Inventory and file ownership

All shared cases live in `libs/conformance/src/stores/<family>.ts`; `case-manifest.ts` declares the independently reviewable expected family/case IDs. The thirteen new transactional families are projects, users, capacity, priorityBands, calendarMarkers, planEvents, workItems, actuals, measures, progress, dependencies, subtrees and journal. The four existing families keep their exact case IDs and bodies unless a specific observation defect is proved. Add savedPlans and savedPlanCapture as two history families. The catalog is nineteen families, not eighteen because users carries two interfaces, and not twenty by counting those interfaces twice.

`source-conformance.ts` composes the kits. `source-declaration.ts` owns capability/exclusion types. `case-runner.ts` separates case execution from Bun declarations. `certification.ts` validates terminal reports. `testing/broken-source.ts` and `testing/faults.ts` are shared test support, with adapter-specific fault controls in each source's `src/testing/`. Shared code imports core ports only; it does not import or instantiate SQLite/memory adapters.

The expected manifest is checked with `satisfies Record<keyof TransactionalStores | keyof HistoryStores, readonly CaseId[]>`. Kit registration is enumerated independently and compared by exact set, so deleting a kit cannot shrink the expected set along with it. Compilation must fail when a new source port lacks a manifest family. Case IDs remain explicit strings `store.method:scenario`; no automatic method-name reflection or percentage coverage claim.

The manifest certifies listed behavioral cases. It does not claim every method/property of a broad port has exhaustive coverage. Existing adapter/service suites remain mandatory and retain behaviors beyond this packet's named cases.

### Fixture and capability protocol

Use the final core `Stores`, `TransactionalStores`, `PlanTransactionalStores`, `HistoryStores`, `Scope`, `UnitOfWork` and `Source` types. The harness shape is:

```ts
type PortName = keyof TransactionalStores | keyof HistoryStores;
interface Gap {
  caseId: CaseId;
  reason: string;
  evidence: { sourceRevision: string; assertion: string; observedFailure: string };
}
type Capability<P> =
  | { kind: 'offered'; open(caseId: CaseId): Promise<CaseFixture<P>>; gaps: readonly Gap[] }
  | { kind: 'absent'; reason: string };
type Capabilities = { [P in PortName]: Capability<Stores[P]> };
interface SourceDeclaration {
  name: string;
  revision: string;
  capabilities: Capabilities;
  historyAdmission: 'immediate-busy' | 'independent-write';
}
interface CaseFixture<P> {
  port: P;
  seed: SeededPlan;
  readers: SourceReaders;
  scenario: ScenarioControl;
  close(): Promise<void>;
}
interface SeededPlan {
  projectIds: readonly [string, string];
  ownerIds: readonly [string, string];
  stepIds: readonly [readonly [string, string], readonly [string, string]];
  workItemIds: readonly [readonly [string, string], readonly [string, string]];
  teamIds: readonly [string, string];
  personIds: readonly [string, string];
  stamps: readonly [WriteStamp, WriteStamp];
}
interface PhaseBarrier {
  entered: Promise<void>;
  release(): void;
}
type ScenarioControl =
  | { kind: 'ordinary' }
  | {
      kind: 'late-write';
      point: 'subtree-final-satellite' | 'journal-history-insert' | 'saved-plan-schedule-body';
      arm(): void;
      reached(): boolean;
    }
  | { kind: 'capture-interleave'; firstRead: PhaseBarrier; changeDirectory(): Promise<void> }
  | { kind: 'competing-history-write'; rivalWriter: SavedPlanStore }
  | {
      kind: 'batch-settlement';
      begin(): Promise<void>;
      entered: Promise<void>;
      settle(decision: 'commit' | 'rollback'): Promise<void>;
    };
```

Each family receives only its typed port plus common deterministic fixture inputs and named scenario support. `SeededPlan` includes two project IDs, two owner IDs, two step IDs per project, two work-item IDs per project, two teams and two people, with explicit WriteStamps at 100 and 200. Family-specific seed records use existing core value types, never unknown dictionaries. Setup writes through source ports where offered, validates the exact resulting IDs/values and completes before fault activation. A source may prepare required companion records through its own adapter fixture when that companion capability is absent; that setup is not certified by this family. Actual assertions read through public ports or explicitly named independent source readers, never a fixture's private array.

`SourceReaders` is an interface of read-only method selections from the actual ports: projects (`findById`, `stepsOf`, `listFor`), workItems/steps/estimates/actuals/measures/progress/dependencies (each `listByProject`), directory (`listTags`, `listTeams`, `listPeople`, `assignmentsFor`, `assignmentsOf`, `assignmentsInProject`), journal (`entriesFor`, `stateOf`), planEvents (`listFor`) and savedPlans (`readOf`, `listOf`, `principalsOf`). Each field is `Pick<Stores['field'], 'method' | ...>`, retaining actual parameter/return types; no copied DTO or generic execute callback. A family requests only its required selections with `Pick<SourceReaders, ...>` in its concrete fixture alias. Providing companion read support does not certify that companion family's writes. `open(caseId)` validates family membership and selects the exact control arm; a missing arm is incomplete, not ordinary by default. The fixture owner starts any held batch/capture barrier only when the case calls the corresponding real operation. Batch `begin` calls the real UnitOfWork, resolves only after its admitted scope is held, and retains its settlement promise; `settle` awaits that promise and rethrows operation failures. Teardown releases every owned barrier before disposing resources, so an assertion failure cannot leave an open transaction.

`ScenarioControl` is a discriminated union of named controls required by the selected case: ordinary, late-write failure, capture interleave, competing history write and batch settlement. Each arm declares its awaited phase and release/observe functions; case definitions narrow the arm rather than assuming optional callbacks exist. Controls are provided by adapter-owned factories. A missing required control means the offered case is incomplete; it is not a skip. Every fixture closes in finally, including setup failure; close errors fail certification rather than being suppressed.

Accountless sources declare users absent. Plan-port signatures cannot gain fake user methods just to satisfy this harness. SQLite offers all nineteen families and no behavioral exclusions. Memory declares offered families and exact supported cases; a fully absent family is reported absent with its reason, while a partial family lists exact gap case IDs. Core C6's staged-source, independent-history and four portable-composition guarantees remain required and cannot be excluded here. Basic saved write/read/capture survival must therefore be offered after that prerequisite lands; incidental adapter-only busy mechanics need not be imitated by memory.

### Execution and report semantics

Keep declaration metadata separate from execution. Each manifest case reaches one terminal state: passed, failed, not-offered or incomplete. Record source/port/case ID, opened fixture identity, execution start/end, assertion phase and failure where applicable. A registered body enters executed when it starts, becomes passed only after all assertions and teardown succeed, and becomes failed on a thrown operation/assertion/cleanup. Catch solely to record context and rethrow. `declared` cannot substitute for `executed` or `passed`.

The full certification target asserts exact expected-case coverage after execution. Missing registrations/bodies, duplicate case IDs, unknown/duplicate gaps, setup errors, teardown errors and nonterminal cases fail it. Focused development runs are explicitly partial reports, never full certification. The full Nx target accepts no test-name filter. A source is certified for exactly its passed offered cases, with absent/gap cases printed separately; it is never simply labeled fully conformant because its passed count exceeds skips.

A gap must reference an existing case and include its reason and actual failing assertion from an isolated run with that exclusion removed. If removing it passes, delete the stale gap. Normal certification need not rerun every known missing feature as an expected failure, but changes to that method or its case invalidate its gap evidence and require a fresh bypass probe. Never add blanket method/port wildcards to hide new failures. Adding actuals/measures/progress missing-step cases must first run them, then either preserve newly observed gaps or fix them in separately authorized implementation; this packet does not require the latter.

### Named broken sources and proof scope

`brokenSource(source, fault)` returns the same source-factory interface with one named fault active after setup. The shared registry uses `FaultId = \`break:${CaseId}\``for one canonical matrix fault per case. For a case with several separately asserted mutations, add explicit literal suffixes to that case's registry entry (for example`break:savedPlans.write:bytes-and-bodies:utf8-length`and`break:savedPlans.write:bytes-and-bodies:header-only`); never accept arbitrary strings. `Fault` is the discriminated union derived from these registered IDs, each carrying its owning case ID and typed adapter control. Registry completeness checks require at least one reachable fault per new or changed check; cases with multiple checks retain all of their separate fault entries. Store/method substitutions retain the real port signature. Wrappers explicitly forward unchanged methods and preserve the receiver of class methods; spreading an instance would lose prototype methods and fail setup rather than the intended assertion. Mutants are never exported by production sources.

For black-box value/scope omissions a typed decorator is sufficient. For transactional claims the source adapter injects the fault **inside** its real operation: SQLite uses an isolated constraint/trigger or the existing connection seam; staged memory uses a test-only failure barrier in its source factory. Throwing from a wrapper after a completed successful transaction is not an atomicity proof. Each faulty run first proves its fixture is reachable and the named phase was entered, then requires the selected assertion to fail. Baseline → fault → restored baseline runs use the same actual shared case, not a duplicated miniature check.

### Independent history and real concurrency

Add cross-family `history.batch:independent-commit` and `history.batch:independent-rollback` to the expected supplemental suite beside existing unit-of-work conformance. Memory's staged source must accept the interleaved history write and assert its exact saved ID remains after either terminal decision. Core C6 already requires that behavior; it cannot be allowlisted.

SQLite can legitimately answer snapshot_busy while another connection holds its write lock. The declaration therefore includes historyAdmission: 'immediate-busy' for SQLite or 'independent-write' for staged memory. The supplemental manifest selects an exact required admission case from that discriminant: `history.batch:busy-does-not-wait` or `history.batch:interleaved-success-survives`, respectively. Both also run preexisting successful-save survival through commit and rollback. Never use `if outcome !== written return` to claim survival ran. The memory arm asserts written before entering its survival assertion; the SQLite arm asserts snapshot_busy while the batch remains held, then verifies an independently successful preexisting save survives settlement. These are named mechanism variants, not SQLite behavioral gaps or permission to skip durability.

Quota races cannot blindly use Promise.all on synchronous bun:sqlite because a waiting BEGIN can block the thread releasing the first one. Reuse the production saved-plan check callback window and immediate-busy second connection from saved-plan-in-transaction.db.test.ts. Memory uses a controlled competing write against the same atomic history state. Both assert one final slot cannot be consumed twice, while mechanism observations remain adapter-specific.

For memory, hold the first write inside its real quota callback, invoke the rival writer without awaiting its outcome from that callback, and release the first callback only after the rival call has been issued. Then await both outcomes. Require the first plan to be written and exactly one new plan in the final public list; the rival must be quota-refused after observing the first plan's updated holding, or must have reported modeled snapshot_busy while the first callback was held. Never accept two written outcomes or an unexplained thrown error. This permits the port's existing contention outcomes without requiring memory to imitate SQLite's lock implementation. With quota checking moved outside the atomic write, both checks can see the old holding and the final exact-ID assertion must fail. The case's held phase and release order are fixed test protocol, not implementer choices.

Capture interleaves use source-specific barriers at the first real snapshot read. A SQLite fault uses its isolated read connection; memory pins a cloned state epoch. The shared assertion reads PlanInputReads only. Transaction atomicity/failure controls remain adapter tests, never a fake transaction reimplementation in the kit.

### Execution targets

Implementation paths are post-core-extraction, pre-namespacing. `libs/conformance/src/*.test.ts` tests manifest/report/fault infrastructure without importing production adapters. `libs/store-sqlite/src/testing/source-conformance.db.test.ts` supplies migrated isolated-file factories; `libs/store-memory/src/testing/source-conformance.test.ts` supplies real staged factories and exact gaps. Both declare `test:conformance` Nx targets; the full source test targets include these files as well. Source-specific faults live next to those factories. `conformance:typecheck` and both source typechecks compile spec projects; lint includes all testing files actually introduced. Namespacing later rewrites the paths through its own manifest.

## Risks / Trade-offs

More kits expose memory lag, which must become named evidence rather than a forced feature implementation. Global source-state leakage or setup writes that erase sentinels can make cross-project checks vacuous; each case opens fresh state and verifies prerequisites before activating its fault. A fully closed family inventory is not complete semantic coverage of every source method. Adapter mechanisms, especially SQLite busy behavior, cannot be inferred from a portable wrapper's success.

## Migration Plan

Close the family/report inventory first; move the four existing families without changing IDs; add the thirteen families in the ordered groups in tasks.md; add two history families and cross-source settlement cases; then validate certification targets, prove every new check and run the integrated gate. No verify.md is produced during preparation.

## Open Questions

No architecture decision is assigned to an implementer. Actual memory gaps and observed fault diagnostics are bounded factual checks. Record exact outcomes; do not guess them or silently broaden a contract.
