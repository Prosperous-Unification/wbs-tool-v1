# HTTP trusted-origin composition preflight

Merged worktree 362c29a8, read-only during parent gate. No source changes, tests or deployment operations. No private .env or secret values read. Sources: be/gw config/main/app, backend boot and auth.routes, public .env.example files, tools/dev/setup.ts, deployment layout/docker allowlists/bootstrap configure.sh, source-dev compose, Playwright config.

## Current sources and missing seam

- Backend BeConfig requires AUTH_MODE local|oidc but has no browser-origin field. main.ts constructs OidcRouteOptions only for oidc. oidcRouteOptionsFromEnv validates AUTH_REDIRECT_URI and callback path, then derives appOrigin from that operator-configured URL. bootBe01 forwards opts.oidc to buildApp.
- Backend global cookie-origin policy runs only when opts.oidc exists. Password login/register origin checks are also conditional on oidc. Consequently the approved always-on login/register policy and unsafe-cookie policy are not represented independently of authentication mode.
- Gateway config has oidcAppOriginFromEnv, deriving the same trusted origin from AUTH_REDIRECT_URI. OIDC wsAuth supplies it to buildApp. Local wsAuth supplies localIdentity and its upgrade branch returns before cookie-origin checking. HTTP Wave1 does not change this gateway-local policy; do not accidentally remove that separate mode contract.
- “Password mode” is not an AUTH_MODE value: accepted modes are local and oidc. Local boot supplies a development identity; OIDC may additionally enable password login/registration behind explicit switches. Tests also build password auth without OIDC. The new HTTP origin policy must cover all these compositions without inventing AUTH_MODE=password.
- Public local examples pin FE at http://localhost:4200, backend3100, gateway3200. The trusted browser origin is the FE/proxy origin, not GW_URL, BE_URL, the backend listener or an arriving Host/Origin header.
- Deployment's trusted layout table tools/tool-remote-scripts/src/lib/env.ts owns prod/dev siteAddress (wbs.bulletpoints.club / dev.wbs.bulletpoints.club). Bootstrap configure.sh independently receives operator SITE_ADDRESS and uses it to author Caddy. These are deployment inputs from which configuration may be written, not application-runtime imports or request-derived values.

## Recommended minimal authorized implementation

1. Give backend boot/buildApp an explicit required appOrigin (or equivalently named trusted browser origin) independent of oidc. Policy runner and login/register consume this one composition value. OidcRouteOptions remains provider configuration; avoid passing divergent origin values to two guards.
2. Resolve the value once at startup from trusted configuration: OIDC retains the already-required validated AUTH_REDIRECT_URI origin; non-OIDC reads a new required APP_ORIGIN. This is a modeled configuration distinction, not a fallback to an untrusted request. It avoids inventing a second mandatory provider setting for existing OIDC deployment while making the missing local/password composition explicit. If implementation instead elects APP_ORIGIN for both modes, wire both carriers in the same slice and assert equality with callback origin; do not leave two inconsistent sources.
3. Validate APP_ORIGIN as an absolute http/https origin without credentials, non-root path, query or fragment; reject missing/empty/malformed/opaque origins. Canonicalize once with URL.origin. The application compares request Origin exactly to that configured origin. No request Host, forwarded host, Origin, GW_URL or backend URL is an acceptable missing-config fallback.
4. Scope the policy exactly as approved: every unsafe request carrying the existing session cookie names receives cookie-origin enforcement, plus login/register regardless of cookies/mode. Preserve safe GET/HEAD/OPTIONS behavior and bearer-only writes without session cookies. Missing Origin on login/register is a refusal under the always rule; callers that currently omit it must change explicitly.
5. Keep gateway behavior unchanged for HTTP Wave1. Its OIDC origin derivation should be included in configuration agreement tests; a shared resolver is only warranted if it keeps auth/provider imports out of contracts and does not pull gateway extraction into this wave.

## Production-path negative matrix to write after freeze

- Both non-OIDC/password test composition and OIDC composition: valid-origin register/login allowed; absent/foreign origin403 invalid_origin before handler verification or cookie issuance. Removing the mode-independent origin check must fail the non-OIDC case.
- Unsafe project and calendar-marker writes carrying session cookie: foreign/missing origin refused with no store mutation; valid configured origin succeeds. Include malformed body to prove policy precedes parsing.
- Bearer-only unsafe write without session cookie retains its existing authorization behavior; GET/HEAD/OPTIONS are not newly refused by cookie-origin policy.
- Resolver: missing/empty/malformed/opaque APP_ORIGIN in local mode fails; correct literal origin accepted. No fallback when request Host/Origin is supplied. OIDC uses configured redirect origin and does not need a new undeclared secret.
- Fresh setup and existing .env upgrade both yield usable config; no unrelated key dropped; missing and unreadable paths distinguished if the upgrade handles them. Break template/upgrade wiring and observe actual config load fail.
- Rendered deploy backend config carries origin when mode requires it; omit injection and watch startup/config-load refusal. Allowlist accepts only intended new nonsecret key and still rejects unrelated secrets.
- Shifted browser server env and baseURL agree. Inject fixed4200 while running a shifted browser login and watch actual403, not merely an equality check computed from the same incorrect value.
- Carry R3 valid token + account-store throw and R5 held login reservation tests unchanged in behavior after new request Origin headers are supplied.
